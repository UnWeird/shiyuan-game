## 2. 六个问题与定位

### L1 棋盘不随视口变大
`GameBoard.tsx:1436` 的 `max-w-7xl`（1280px）+ `GameBoard.tsx:1954` 的硬编码 `height: '700px'`。
**1920 与 1440 下棋盘像素完全相同**（744×664）。1920 上棋盘只占视口宽 39%，左右各 320px 死边。

> 注：`client/src/App.css` 里的 `#root { max-width: 1280px }` **不是**原因 ——
> 该文件全项目无人 import，`#root` 的 computed `max-width` 实测为 `none`。它是死文件，应删。

### L2 容器长宽比与棋盘不符
棋盘 viewBox 为 `772.82 × 680` = **1.1365 : 1**；容器 `956×700` = 1.37 : 1。
SVG 按高度适配，左右各空 89px。这是"棋盘漂在大黑框里"的几何原因。

### L3 操作按钮离棋盘 400–670px
每个动作是三段行程：点棋子 → 右栏按钮 → 回到目标格。1440 下单程 671px。
手机上按钮在棋盘下方**且在首屏之外**，每次操作都要滚动。

### L4 常见视口都要滚动
1440×900 超 221px（战报完全不可见）· 1024×768 超 411px · 375×812 超 **768px**（页面≈2 倍视口）。
手机 HUD 占 236px = 视口高 **29.1%**，棋盘只剩 35%。

### L5 HUD 内部没有对齐基线
实测七个元素的垂直中心：

```
行动阶段 101 · 规则/音效 85 · 部署价值 61 · 2.1元 85 · 行动点 41 · 基础:2个 94 · 结束回合 85
```

「行动点」标签比其余元素高 **44px**，骰子又挂在更下面。七个元素五条中心线。

### L6 右栏被 `maxHeight: 700px` 截断
`GameBoard.tsx:1931`。820×1180 下视口有 1180 高，面板硬截到 700 → 将军技能按钮被切掉一半，
需要在面板内二次滚动。且行动阶段仍显示整块「部署单位」，与当前可做的事无关。

## 3. 方案

### 3.1 棋盘尺寸：三行 CSS 解决

```css
.board-wrap { container-type: size; flex: 1; min-height: 0; min-width: 0; display: flex; }
.board      { width: min(100cqw, calc(100cqh * var(--board-ar)));
              aspect-ratio: var(--board-ar); margin: auto; }
```

`--board-ar: 1.1365`。这等价于 `min(可用宽, 可用高 × 比例)`，既吃满空间又永不溢出。
**删掉 `max-w-7xl` 与 `height: 700px`。**
（`cqw/cqh` 需 Chrome 105+ / Safari 16+；项目是 Vite + 现代浏览器，无需兜底。）

### 3.2 桌面结构

```
┌─────────────────────────────────────────────┬──────────────┐
│ HUD 48px  回合·阵营·行动点·骰子·结束回合         │              │
├─────────────────────────────────────────────┤  选中单位     │
│                                             │ 令牌放大 +     │
│                 棋盘                         │ 通道图解       │
│            吃满剩余空间                        │              │
│                                             │  战报         │
│         （操作用棋子旁径向菜单）                 │ 首屏内可见     │
└─────────────────────────────────────────────┴──────────────┘
```

- HUD **138px → 48px 单行**，所有元素共享一条基线。部署价值/骰子/基础收进可点开的小面板。
- 右栏 `flex: 0 0 clamp(264px, 22%, 400px)`，吸收宽屏余量；删掉 `maxHeight: 700px`，改 `height:100%` + 分区滚动。
- 右栏只留「选中单位 + 战报」；部署面板**只在部署阶段**出现。

### 3.3 操作方式：径向菜单 > 底部动作条

选中棋子后在棋子周围开一圈动作按钮（半径 ~52px）。实测行程对比（1440×900）：

| 方式 | 行程 | 棋盘面积 |
|---|---|---|
| 现状（右栏按钮） | 678px | 基准 |
| 底部动作条 | 412px | +26% |
| **棋子旁径向菜单** | **52px** | **+49%** |

径向菜单不仅把行程降到 1/13，还因为省掉动作条那一行高度，让棋盘再大一圈。

### 3.4 侧栏断点必须是 1024，不是 768

现有 `useIsNarrowScreen` 默认 `breakpoint = 768`。**一条右栏在 820px 视口下站不住**：
初版提案在 820 下右栏吃掉 264px，棋盘反而比现状小 7%。把侧栏布局的下限提到 **1024** 之后：

| 820×1180 | 棋盘 | 占视口高 |
|---|---|---|
| 现状 | 553×487 | 41.2% |
| 提案（断点 768，错） | 516×454 | 38.5% ❌ |
| 提案（断点 1024，对） | 804×707 | **60.0%** ✅ |

`useIsNarrowScreen(768)` 本身不改（点击热区等用途仍需要 768），
**新增一个 `useHasSideRail()` 用 1024** —— 两个断点语义不同，不要复用。

### 3.5 手机：棋盘是宽度受限，不是高度受限

这条修正了一个直觉错误。375 宽的屏幕上，1.1365:1 的棋盘最大只能是 `359×316`，
占视口高 **38.9%** —— 不管怎么压缩 HUD 都到不了 55%。

结构（已能做到零滚动）：

```
HUD 44px → 棋盘 → 选中单位单行摘要 76px → sticky 动作条 56px → 战报（默认折叠 38px）
```

| 375×812 | 棋盘 | 占视口高 | 滚动 |
|---|---|---|---|
| 现状 | 323×284 | 35.0% | 超 550px |
| 提案 · pointy-top | 359×316 | 38.9% | **0** |
| 提案 · **flat-top 转 90°** | **359×408** | **50.2%** | **0** |

### 3.6 ⚠️ 待单独评估：竖屏下把棋盘转成 flat-top

棋盘转 90°（pointy-top 1.1365:1 → flat-top 0.88:1）在手机上让棋盘面积 **+106%**（对比现状）。
宽屏上相反——1920 下 flat-top 只有 873×992 而 pointy-top 有 1127×992，所以应当**跟随视口朝向**：

```
横向视口 → pointy-top     竖向视口 → flat-top
```

**但这不是纯渲染改动**，必须单独评估：

1. `hexCorners()` 的顶点角 `60i+30` 要改 `60i`，`hexToPixel` 的 x/y 公式互换；
2. `Direction` 的 8 个方向（含正北/正南）与 `UnitPiece` 的 `angleMap` 要整体旋转 90°；
3. 起始区 `r >= 3` 在视觉上会从"下方三排"变成"右侧三列"，
   `BaseSetup` 的提示文案「在上方起始区选择」要跟着改成左/右；
4. 机关占位（弩车倒 V、战车/投石车）的"前后方"定义依赖朝向，需逐个核对。

收益很大，但牵涉方向系统，**建议作为独立一期**，不要和布局重构混在一起做。

## 4. 预期收益（mockup 实测，径向菜单 + 断点 1024）

| 视口 | 棋盘面积变化 | 滚动 | 行程 |
|---|---|---|---|
| 1920×1080 | **+122%** | 41px → **0** | 671 → **52px** |
| 1440×900 | **+49%** | 221px → **0** | 671 → **52px** |
| 1366×768 | +4% | 353px → **0** | 678 → **52px** |
| 1024×768 | +4% | 353px → **0** | 543 → **52px** |
| 820×1180 | **+111%** | 0 → 0 | 438 → **52px** |
| 375×812 | +24%（flat-top 则 +106%） | 550px → **0** | 344 → **52px** |

1366 / 1024 这两档棋盘几乎不变大 —— 因为视口只有 768 高，棋盘本来就已经被高度吃满。
它们的收益在**零滚动**和**行程**上。

## 5. 分期

| 期 | 内容 | 风险 |
|---|---|---|
| **P0** | 删 `max-w-7xl` / `height:700px` / `maxHeight:700px`；棋盘改容器查询尺寸；删死文件 `App.css`；修「类型/生命/行动」黑字黑底与枚举值外显 | 低，纯 CSS/样式 |
| **P1** | HUD 压成 48px 单行并统一基线；右栏只留选中单位 + 战报；部署面板只在部署阶段显示；新增 `useHasSideRail()`（1024） | 中，动结构 |
| **P2** | 径向菜单替代右栏按钮（含键盘 / 触摸热区 ≥44px） | 中，动交互 |
| **P3** | 竖屏 flat-top（见 §3.6） | 高，动方向系统 |

## 5.1 P0 实现记录（已完成，实机实测）

同一局面（行动阶段，17 个单位）下改动前后对比：

| 视口 | 改前棋盘 | 改后棋盘 | 面积 | 改前滚动 | 改后滚动 |
|---|---|---|---|---|---|
| 1920×1080 | 744×664 | **986×867** | **+73%** | 41px | **0** |
| 1440×900 | 744×664 | **781×687** | **+8%** | 221px | **0** |
| 1366×768 | 757×666 | 631×555 | −30% ⚠️ | 353px | **0** |
| 1024×768 | 694×619 | 565×497 | −35% ⚠️ | 411px | **0** |
| 820×1180 | 553×487 | **770×678** | **+94%** | 0 | **0** |
| 375×812 | 323×284 | **333×293** | **+6%** | 550px | **0** |

**1366 / 1024 两档棋盘变小了**，这是把整页压进一屏的直接代价：
这两个视口只有 768 高，原来棋盘能有 666 是因为页面往下滚了 350+px、战报被挤到首屏外。
现在棋盘 + 右栏 + 战报全要塞进 768 高，而 HUD 还占着 122px。

**这一档要靠 P1 的 HUD 压缩补回来**：HUD 122px → 48px 能把 74px 还给棋盘，
1024×768 下棋盘回到约 650×572（与改前持平且不滚动）。
mockup 里 1366/1024 的"+4%"假设 HUD 已经是 48px，所以 P0 阶段达不到。

实现偏差一处：**`useHasSideRail()`（1024 断点）原排在 P1，提前到 P0 做了** ——
不做的话 820×1180 会从 553×487 退到 482×424，P0 不能带着退化上线。

## 5.2 P1 实现记录（HUD 部分已完成）

HUD 从 138px 压到 **68px 单行**，做法：

- 回合标题与阶段并到一行，阶段降为灰色后缀
- 将领徽章去掉「朱红 / 青玉」那一行，阵营靠名字颜色区分
- 「部署价值 / 行动点」从三行堆叠改成 `label: value` 单行
- 骰子从「行动点」块里独立出来；「基础 N 个 / 击杀奖励 / 永久失去」的明细挪进 `title`
- 「规则 / 音效」收成 32×32 图标按钮（带文字时两个要 124px，正是它们在 1024 宽下把 HUD 挤成两行）

| 视口 | HUD 改前 | 改后 | 行数 | 中心线极差 |
|---|---|---|---|---|
| 1920 / 1440 / 1366 / 1024 | 138 / 138 / 138 / 122 | **68** | 1 | **0.0px** |
| 820×1180 | ~122 | 110 | 2 | 50px |
| 375×812 | **236** | **150** | 3 | 92px |

棋盘尺寸（对比**改动前的原始实现**）：

| 视口 | 原始 | P0 | P1 | 相对原始 |
|---|---|---|---|---|
| 1920×1080 | 744×664 | 986×867 | **1066×938** | **+43% 线性 / +102% 面积** |
| 1440×900 | 744×664 | 781×687 | **861×758** | **+16% / +32%** |
| 1366×768 | 757×666 | 631×555 | 711×626 | −6% / −12% |
| 1024×768 | 694×619 | 565×497 | 686×604 | −1% / −4% |
| 820×1180 | 553×487 | 770×678 | 770×678 | **+39% / +94%** |
| 375×812 | 323×284 | 333×293 | 333×293 | +3% / +6% |

六档视口**全部零滚动**。1366 仍差 6%：它只有 768 高，棋盘已被高度吃满，
再要变大只能动棋盘容器的内边距，收益有限。

**一处规格判断被实现推翻**：§3.2 写的"部署面板只在部署阶段出现"是错的。
`handleStartDeploy` 由行动点闸控 —— **中局补兵是真机制**，藏掉等于删功能。
改成可折叠：部署阶段默认展开，行动阶段收起并在标题带剩余兵力摘要
（`部署单位  步6 · 骑3 · 弓2`），兵力用尽则整块不渲染。折叠态 62px，展开 250px。

## 6. 验收标准

| # | 检查项 |
|---|---|
| 1 | 1920 / 1440 / 1366 / 1024 / 820 / 375 六档视口下 `document.body.scrollHeight <= innerHeight` |
| 2 | 1920 下棋盘绘制宽度 ≥ 1000px（现状 744） |
| 3 | 棋盘绘制尺寸的长宽比与 viewBox 之差 < 0.5% |
| 4 | HUD 内所有元素的垂直中心落在同一条线（极差 < 2px） |
| 5 | 选中棋子后，最近动作按钮中心与棋子中心距离 ≤ 80px |
| 6 | 触摸目标（动作按钮、格子）最小边 ≥ 44px |
| 7 | 行动阶段 DOM 中不存在「部署单位」面板 |
| 8 | 所有文字对比度 ≥ 4.5:1（当前「类型/生命/行动」为 1.04:1） |
